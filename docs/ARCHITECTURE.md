# Architektura

```text
Vue 3 / Vite → ASP.NET Core API → Azure DevOps REST API
```

Frontend wybiera projekt i repozytorium, wyświetla aktywne PR-y i szczegóły. W developmentcie Vite przekazuje żądania `/api` do backendu.

Backend jest podzielony na cztery projekty, a zależności wskazują do środka:

```text
PRCockpit.Api  →  PRCockpit.Application  →  PRCockpit.Domain
      ↓                      ↑
PRCockpit.Infrastructure ────┘
```

- **Domain** — modele PR-a, pakiet kontekstu, stan review i reguły takie jak `TextLineLimit`. Nie zna HTTP, bazy, Roslyna ani ASP.NET.
- **Application** — porty (`IAzureDevOpsClient`, `IAiSummaryAnalyzer`, `ICSharpHoverAnalyzer`, trzy magazyny) oraz logika przypadków użycia: `PrContextBuilder`, `SummaryRunner`, `PullRequestContextService`, `SummaryService`. Sekwencja „pobierz szczegóły → zbuduj kontekst → uruchom AI → zapisz” ma tu jednego właściciela, zamiast siedzieć w ciele endpointu.
- **Infrastructure** — adaptery: `AzureDevOpsClient` i `AzureDevOpsMapper`, `CliSummaryAnalyzer`, Roslyn w `CSharpHovers`, `PrCockpitContext` z encjami i migracjami oraz trzy magazyny. `InfrastructureServices.AddInfrastructure` jest jedynym miejscem, które wiąże port z konkretną implementacją.
- **Api** — host: rejestracja zależności, trasy i `Execute`.

Kierunek zależności nie jest deklaracją — pilnuje go `ArchitectureTests`, który czyta faktyczne referencje zestawów i sprawdza, że domena nie zna EF, SqlClient, Roslyna, ASP.NET ani HTTP, że aplikacja nie zna infrastruktury i że każdy port ma adapter. Złamanie warstwy wywraca test, a nie tylko konwencję.

Aplikacja nie ma uwierzytelniania i świadomie go nie dostanie: to narzędzie jednej osoby na jednej maszynie. Dlatego `LocalOnly` sprawdza przy starcie adres nasłuchu (`urls`, `ASPNETCORE_URLS`, `Kestrel:Endpoints:*:Url`) i **nie pozwala wstać** serwerowi na adresie innym niż pętla zwrotna — kto dosięgnie portu, ten komentuje tokenem właściciela. `*`, `+` i `0.0.0.0` liczą się jako adres zewnętrzny: `Uri` ich nie parsuje, a to one otwierają port na sieć. Świadome wyłączenie to `Security:AllowRemoteAccess=true`, które startuje z ostrzeżeniem.

Backend czyta organizację i PAT z konfiguracji .NET (User Secrets lub zmienne środowiskowe). Frontend nie otrzymuje PAT. Integracja używa Azure DevOps REST API 7.1 i pobiera dane na żądanie. Dla szczegółów PR pobiera ostatnią iterację, listę zmienionych plików, commity i powiązane Work Items. Lista plików korzysta z porównania ostatniej iteracji z bazą PR i obsługuje strony zmian; licznik wynika z długości listy. Commity są pobierane przez [endpoint PR commits](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-commits/get-pull-request-commits?view=azure-devops-rest-7.1) z `continuationToken`; odpowiedź szczegółów zawiera ich ID, wiadomość, autora i opcjonalną datę, a `commitsCount` wynika z długości tej listy.

Po kliknięciu pliku frontend wywołuje osobny endpoint diffu. Backend ponownie pobiera ostatnią iterację i listę zmian (`$compareTo=0`), aby zaakceptować wyłącznie plik należący do PR. Wersja przed zmianą pochodzi z `commonRefCommit` tej iteracji, a wersja po zmianie z `sourceRefCommit`; przy przeniesieniu pliku wersja bazowa używa `originalPath`. Dla dodania i usunięcia jedna strona jest pusta. [Dokumentacja iteracji](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-iterations/list?view=azure-devops-rest-7.1) i [porównania zmian](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-iteration-changes/get?view=azure-devops-rest-7.1) opisują te punkty odniesienia.

Backend pobiera metadane pliku z [Git Items Get](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/items/get?view=azure-devops-rest-7.1) dla konkretnego commita, potem strumień z [Git Blobs Get Blob](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/blobs/get-blob?view=azure-devops-rest-7.1). Odrzuca pliki binarne, symlinki, pliki ponad 256 KB na wersję i tekst przekraczający 4000 linii łącznie. Endpoint `/diff` zwraca w jednym JSON pola `path`, `originalPath`, `kind`, `originalText` i `modifiedText`. Dla `kind: text` oba teksty są dostępne, włącznie z pustą stroną przy dodaniu lub usunięciu. Dla `binary` i `tooLarge` oba pola tekstowe są `null`; frontend pokazuje komunikat. Nie przechowujemy zawartości plików.

Endpoint `/api/projects/{project}/repositories/{repositoryId}/pull-requests/{pullRequestId}/context` buduje na żądanie deterministyczny pakiet wejściowy do Summary. Zwraca metadane PR, `baseCommitSha` i `headCommitSha` ostatniej iteracji, tytuły commitów oraz każdy zmieniony plik z typem zmiany. Tekstowy diff ma formę obu wersji pliku (`originalText`, `modifiedText`), taką samą jak istniejący endpoint `/diff`. `PrContextBuilder` dołącza oba teksty tylko w całości: limit to 20 000 znaków UTF-16 na plik i 100 000 znaków UTF-16 dla wszystkich tekstów diffów w PR. Metadane i tytuły commitów nie wchodzą do tego budżetu. Po pominięciu treści zostają ścieżka, typ zmiany i `omissionReason` (`lockFile`, `snapshot`, `generated`, `minified`, `buildOutput`, `binary`, `sourceTooLarge`, `fileCharacterLimit` lub `pullRequestCharacterLimit`). Flaga `wasLimited` sygnalizuje co najmniej jedno pominięcie. Sam pakiet nie obcina tekstu i nie wywołuje AI. Wszystkie zawartości są pobierane z commitów ostatniej iteracji, a lista zmian i iteracja są pobierane raz dla pakietu.

`POST /api/projects/{project}/repositories/{repositoryId}/pull-requests/{pullRequestId}/summary` jest jedyną ścieżką uruchamiającą AI. Buduje świeży `PrContext` i przekazuje go przez `IAiSummaryAnalyzer` do `CliSummaryAnalyzer`. Backend uruchamia skonfigurowany program bez powłoki, przesyła JSON przez stdin, odbiera tylko JSON przez stdout i egzekwuje timeout oraz limit 131 072 znaków odpowiedzi (sufit ustawia największy PR, bo `readingOrder` ma jedną linię na plik; to nadal sufit na ucieczkę adaptera, tylko taki, którego prawdziwa odpowiedź nie dotyka). Stała instrukcja jest oddzielona od niezaufanego pola `context`; CLI nie dostaje ścieżki do lokalnego repozytorium. `SummaryRunner` sprawdza wersję schematu, liczbę zdań (2–5) i limit długości każdego zdania. Odpowiedź dla UI zawiera wynik, osobne zdania, SHA głowy i raport uwzględnionych oraz pominiętych plików. Po walidacji wynik jest zapisywany w SQLite. Spóźniona odpowiedź nie zastępuje wyniku innego PR w bieżącej karcie. Brak konfiguracji CLI, timeout, błędny JSON i niepoprawny wynik zwracają jawny błąd.

`GET .../summary` odczytuje ostatni zapisany wynik bez uruchamiania AI. `SummaryStore` zapisuje odpowiedź i czas zapisu pod kluczem organizacja/projekt/repozytorium/PR w tej samej bazie SQLite co checklisty. Zapisany `headCommitSha` jest porównywany w UI z SHA bieżących szczegółów PR. Przy różnicy wynik pozostaje widoczny z ostrzeżeniem o nieaktualności; gdy brakuje SHA, UI informuje, że nie może potwierdzić aktualności. Ponowne generowanie nadal wymaga kliknięcia i zastępuje zapis dopiero po udanej analizie. Zdania Summary są wyświetlane jako osobne akapity bez interpretowania Markdown ani dodatkowej analizy.

Frontend ładuje Monaco Diff Editor dopiero po wybraniu pliku tekstowego. Edytor jest tylko do odczytu, dobiera język po ścieżce pliku (z fallbackiem do zwykłego tekstu), używa osobnych workerów dla obsługiwanych języków i domyślnie pokazuje diff w jednej kolumnie, z przełącznikiem na widok obok siebie (`renderSideBySide` zmieniane przez `updateOptions`, bez odtwarzania edytora). Niezmienione fragmenty pliku są zwijane natywnym `hideUnchangedRegions`, a po pierwszym przeliczeniu diffu widok ustawia się na pierwszej zmianie (`revealFirstDiff`); ta subskrypcja zwalnia się po jednym wywołaniu, żeby kolejne przeliczenia nie przesuwały widoku czytelnikowi. Komponent sam wybiera motyw: definiuje parę `pr-cockpit-code` i `pr-cockpit-code-dark` z jednej tabeli tokenów i przełącza ją przez `matchMedia`, dzięki czemu App.vue nie nasłuchuje na media query. Przy zmianie pliku lub opuszczeniu widoku PR zwalnia edytor i oba modele. Lista plików, wyszukiwanie i ręczny znacznik „Obejrzałem” pozostają obok diffu; otwarcie pliku nie zmienia znacznika. Przepływ jest sprawdzony testami HTTP bez prawdziwego Azure DevOps; użytkownik potwierdził też działanie diffu na rzeczywistej organizacji, bez osobnego raportu o wszystkich przypadkach brzegowych.

Dla plików C# frontend wysyła oba już pobrane teksty diffu raz do `POST /api/csharp/hovers`. Backend używa Roslyn do ustalenia symboli i typów w każdym tekście osobno, a Monaco przypisuje podpowiedzi i semantyczne kolory nazw do odpowiednich modeli. Klasy, metody, pola, właściwości, parametry i zmienne mają odrębne kolory; gdy symbol zależny od innych plików pozostaje nierozstrzygnięty, proste konstrukcje składniowe nadal pozwalają pokolorować nazwę klasy lub wywołania. Żądanie podlega limitom rozmiaru i liczby linii diffu. Analiza nie pobiera całego projektu ani jego zależności, dlatego pomija podpowiedzi typów, których nie może wiarygodnie ustalić. Przy zamknięciu pliku frontend przerywa żądanie i usuwa dostawców podpowiedzi oraz kolorowania. Motyw Monaca zachowuje bazowe kolory słów kluczowych, komentarzy i tekstów, nadaje identyfikatorom C# i TypeScript ciemnoniebieski odcień oraz dodatkowo wyróżnia nazwy typów w TypeScript.

Ręczny znacznik „Obejrzałem” jest przechowywany tylko w pamięci bieżącej karty i znika po odświeżeniu. Filtr nieobejrzanych i akcja przejścia do następnego pliku działają na bieżących wynikach wyszukiwania; nawigacja nie zaznacza pliku automatycznie. Frontend ignoruje odpowiedzi z wcześniejszych żądań po zmianie projektu, repozytorium lub PR, żeby stara lista nie zastąpiła bieżącej. Test interakcji obejmuje filtr, nawigację i tę zmianę repozytorium; wygląd na wąskim ekranie nadal wymaga sprawdzenia w przeglądarce.

Widok otwartego PR jest trybem czytania, a nie długą stroną. Nagłówek `.pr-header` mieści powrót do listy, numer i tytuł, status, gałęzie, autora oraz postęp checklisty. Poniżej `.pr-workspace` dzieli ekran na trzy niezależnie przewijane panele o wysokości okna: lista plików, diff i szyna kontekstu (`.context-rail`) z Summary, checklistą, ścieżką kluczowych plików, commitami i szczegółami PR w natywnych `<details>`. Selektory projektu i repozytorium znikają po otwarciu PR. Tryb skupienia (`f`) chowa szynę, dlatego licznik checklisty stoi w nagłówku, a nie w szynie — sekcja w szynie ma same pola, bez powtórzonego `N / 6`. Nagłówki sekcji szyny (`.summary-heading`, `.rail-block > summary`) są przyklejone, bo przy przewinięciu tekst Summary zaczynał się w środku zdania, bez nagłówka nad sobą. Poniżej 900 px panele układają się w kolumnę, a diff idzie na górę.

Lista zmienionych plików jest drzewem folderów budowanym w `src/fileTree.ts` i renderowanym rekurencyjnie przez `FileTree.vue` na natywnych `<details>`, więc zwijanie nie trzyma żadnego stanu w aplikacji. Łańcuchy folderów, które zawierają wyłącznie jeden podfolder, są scalane w jedną etykietę — przy PR, gdzie wszystkie pliki dzielą głęboki prefiks, oszczędza to kilka poziomów wcięcia. Drzewo powstaje z plików już przefiltrowanych przez wyszukiwanie i przełącznik „Nieobejrzane”, więc zawsze opisuje dokładnie to, co widać. Folder w całości przeczytany zwija się sam, chyba że trwa wyszukiwanie albo zawiera otwarty plik. Przy filtrze „Nieobejrzane” licznik pokazuje samą liczbę plików zamiast proporcji, bo wszystkie widoczne pliki są wtedy z definicji nieprzeczytane. Wiersz drzewa oddaje szerokość nazwie pliku: typ zmiany jest jedną literą z całym słowem w `title`, obejrzany plik **gaśnie** (nazwa i znacznik na `--text-muted`) zamiast zapalać drugą zieleń obok zaznaczenia, a opis roli pliku pokazuje się tylko przy pliku, na którym stoisz — w każdym wierszu naraz łamał się na dwie linie i podwajał długość drzewa. Woła wyłącznie wariant „✓ zmienione”, bo tam jest co zrobić. `flattenTree` daje kolejność renderowania i to **ona** steruje nawigacją `j`/`k` oraz akcją „następny nieobejrzany”, żeby „następny” znaczyło następny widoczny, a nie następny z kolejności zwróconej przez Azure DevOps.

Trzecim filtrem drzewa — obok wyszukiwania i „Nieobejrzane” — jest **„Pokaż zmiany”: co przyszło po wybranej aktualizacji**. Azure DevOps grupuje commity w iteracje (jedna na push) i porównuje wyłącznie całe iteracje, więc filtr jest per iteracja, opisany tytułem commita zamykającego ją; commita ze środka pushu nie da się odseparować bez liczenia diffu commit-do-commita u siebie. `GET .../changed-paths?sinceIteration=N` woła `/iterations/{ostatnia}/changes?$compareTo=N` — ten sam parametr `$compareTo`, który przy wartości 0 daje cały PR — i zwraca **same ścieżki**, bo przeglądarka ma już wiersze i potrzebuje tylko wiedzieć, które zostawić. Wybór iteracji równej ostatniej zwraca pustą listę bez żadnego żądania o zmiany; iteracja spoza PR to 404. Filtr ma własny licznik żądań, więc spóźniona lista z poprzedniego PR nie zawęża bieżącego, a błąd **kasuje filtr i mówi o tym** — filtr, który po cichu pokazuje wszystko, kłamie gorzej niż jego brak. `openFile` bierze ten sam numer iteracji, więc otwarcie pliku z zawężonego drzewa pokazuje wyłącznie to, co dopisano po tej aktualizacji, a przycisk „Pokaż cały diff” wraca do pełnego porównania bez wyłączania filtru. Skok do wątku komentarza zawsze otwiera pełny diff: wątek jest zakotwiczony w linii całego pliku, której w zawężonym diffie może nie być.

Zapis komentarzy przechodzi tą **samą** ścieżką co odczyt: `SendAsync` ma opcjonalne `method` i `body`, a walidacja organizacji i PAT istnieje w jednym egzemplarzu. Zapis jest za wyłącznikiem `AzureDevOps:AllowComments` (domyślnie false), sprawdzanym zanim cokolwiek opuści maszynę, i mapuje błędy inaczej niż odczyt: 401/403 → 503 z nazwą brakującego zakresu PAT, 400 → 400, 409 → 409. Zakres to założenie wątku, odpowiedź, status oraz **edycja i skasowanie własnego komentarza** — Azure DevOps pozwala na jedno i drugie tylko autorowi, więc `isMine` decyduje, czy akcje w ogóle się pokazują. W UI obowiązują dwa kroki i brak zapisu optymistycznego: przycisk blokuje się, żądanie leci, wątki są czytane ponownie.

Widok komentarzy jest trzecim trybem środkowego panelu (obok diffu i opisu PR), z wyszukiwarką, filtrem i grupowaniem po pliku w kolejności drzewa. Znaczniki w diffie stoją na marginesie **edytora zmodyfikowanego** — przy diffie w linii tylko prawa strona ma adresowalne pozycje. Komentarz zakłada się kliknięciem w linię: najechanie pokazuje `+` na marginesie, klik w margines albo w numer linii otwiera rozmowę, a szkic i wątek renderują się **nad diffem**, żeby kod nie znikał z ekranu. Nad diffem stoi też pasek ze wszystkimi wątkami tego pliku, a drzewo plików niesie odznakę `💬 N` sumowaną przez foldery. „Rozwiązany” znaczy `fixed`, `wontFix` albo `closed` — wątek bez statusu liczy się jako czekający; resolve jest osobną akcją, a „Odpowiedz i rozwiąż” wysyła odpowiedź przed zmianą statusu. Skasowany komentarz przychodzi z Azure DevOps bez treści i **nie jest pokazywany**: wiersz mówiący wyłącznie „coś tu kiedyś było" rozbijał rozmowę, nic do niej nie wnosząc. Filtr stoi w jedynym miejscu, w którym wątki wchodzą do stanu (`withoutDeleted` w `loadThreads`), więc liczniki, odznaki w drzewie i znaczniki na marginesie edytora idą za nim same — wszystkie liczą z tej samej listy. Wątek, którego wszystkie komentarze skasowano, znika w całości. Typ `ReadableThread` niesie tę gwarancję dalej, dzięki czemu szablony nie pytają już, czy komentarz ma treść. Treść komentarzy renderujemy jako Markdown tym samym torem co opis PR (`markdown-it` z `html:false` + DOMPurify) — to ta sama klasa niezaufanego tekstu, więc druga powierzchnia sanityzacji nie powstaje. Komentarze renderują się **pomiędzy liniami kodu** jako Monaco *view zones*: kontener tworzy `MonacoDiff` i oddaje przez zdarzenie `zones`, a treść wjeżdża tam `<Teleport>`em, więc pozostaje zwykłym Vue. Strefy dodajemy i usuwamy pojedynczo i odtwarzamy po `onDidUpdateDiff`, bo diff editor przelicza wtedy własne strefy — to świadome odwrócenie zalecenia z PLAN.md §4.5 wariant C. Każda strefa dostaje pusty bliźniak o tej samej wysokości w edytorze oryginalnym: oba edytory przewijają się w parze, a każdy przycina pozycję do własnej wysokości treści, więc bez bliźniaka lewa strona kończyła się pierwsza i ściągała prawą z powrotem — w pliku z komentarzem nie dawało się dojechać do końca. Bliźniak trzyma też oba panele w równi przy diffie obok siebie. Każdy blok zwija się osobno. Plik bez diffu tekstowego nie ma edytora, więc tam zostaje blok dokowany nad diffem; przewija się, ma natywne `resize` i nigdy nie ucina treści. Otwarcie wątku przewija edytor do jego linii. Każdy wątek w widoku komentarzy pokazuje kod, którego dotyczy: trzy linie kontekstu i linia zakotwiczenia, z **jednego diffu na plik** trzymanego w pamięci, dopóki PR jest otwarty. Wątek niesie iterację, na której powstał; porównanie jej z ostatnią iteracją daje etykietę „kod zmienił się po tym komentarzu”, a `GET .../diff?path=…&sinceIteration=N` pokazuje różnicę między commitem tamtej iteracji a głową. Numer iteracji, nie SHA, jest tym, co przychodzi z przeglądarki — commit rozwiązuje backend z listy iteracji tego PR.

Front pyta backend o `GET /api/config` raz przy starcie i dostaje jedną flagę `commentsEnabled` z `AzureDevOps:AllowComments`. Gdy pisanie jest wyłączone, akcje zapisu w ogóle się nie pokazują (`.pr-workspace--readonly`), zamiast być wyszarzone — wyłącznik przestaje być czymś, co poznaje się z 503 po napisaniu komentarza. Sonda jest miękka: każdy jej błąd zostawia pisanie włączone, bo bramką pozostaje backend. `Esc` odkleja jedną warstwę naraz (pomoc → usuwanie → edycja → szkic → rozmowa → widok komentarzy → tryb skupienia → lista) i działa również wewnątrz pola szkicu; w pozostałych polach tylko zdejmuje focus. Nagłówek PR niesie licznik nierozwiązanych wątków, bo w trybie skupienia szyna znika.

Wątek zakotwiczony w linii wysyła **oba końce zakresu** — `rightFileStart` i `rightFileEnd`, offsety 1 i 2, czyli jednoznakowy zakres z przykładu Microsoftu. Sam `rightFileStart` jest przez API przyjmowany bez słowa, a potem wywraca **webowy UI Azure DevOps**, który przy renderowaniu wątku czyta `rightFileEnd.line` i dostaje `undefined`; komentarz wystawiony stąd zepsuł stronę PR wszystkim, którzy patrzyli na nią w przeglądarce. Komentarz do całego pliku nie ma zakresu w ogóle — to inny kształt, a nie wypełniony do połowy. Payload jest zapięty testem, bo to jest zapis do cudzego systemu.

Odczyt wątków (`GET .../threads`) jest osobną ścieżką od zapisu opisanego wyżej i nie wymaga rozszerzonego PAT. Mapper wątków jest jedynym w tym projekcie, który jest surowy tylko na `id` — wątki systemowe przychodzą bez `status`, a skasowane komentarze bez `content`, więc surowość w pozostałych polach zamieniłaby jeden wątek systemowy w błąd całej listy. Wątki systemowe odfiltrowuje backend. Komentarze **nie** wchodzą do `PrContext` i nigdy nie trafiają do modelu.

Adapter nie przepuszcza surowego stdout modelu dalej: „zwróć tylko JSON" jest prośbą do modelu, a nie gwarancją, i na tym samym strumieniu potrafi wylądować płot ```json, zdanie wstępu albo notka samego CLI. `scripts/extract-json.mjs` wyjmuje z odpowiedzi zewnętrzny obiekt `{…}`, licząc klamry poza literałami tekstowymi; czego nie rozumie, oddaje bez zmian, żeby backend zalogował to, co naprawdę przyszło. Backend przy nieudanym parsowaniu loguje pierwsze 400 znaków stdout i stderr adaptera na poziomie Warning — do klienta nadal nie trafia nic z tej treści, ale 502 „AI CLI returned invalid JSON" przestał być komunikatem, z którym nie da się nic zrobić.

Druga ścieżka AI to wyjaśnienie **jednego** pliku: `task: "file"` w tym samym adapterze, kontekst zawężony przez `onlyPath` w `PrContextBuilder` (te same budżety), walidacja na 1–3 zdania, ścieżka brana z kontekstu. `POST .../summary/file` przyjmuje ścieżkę w ciele i sprawdza ją względem listy plików PR, zanim cokolwiek poleci dalej. Wynik leży w `pr_file_explanations` pod kluczem PR + ścieżka, z **identyfikatorem blobu** i SHA głowy jako kolumnami. O nieaktualności decyduje `ContentFreshness` w warstwie Domain: inny blob znaczy „ten plik się zmienił”, a gdy blobu nie ma po którejś stronie — inna głowa PR. To ta sama reguła, którą stosuje znacznik „Obejrzałem”, i dokładnie dlatego istnieje: porównanie po samej głowie kasowało wyjaśnienia **wszystkich** plików po jednym commicie (NIESP-04), co przy prefetchu ścieżki byłoby ośmioma uruchomieniami modelu zamiast jednego. Reguła znacznika liczy się nadal w przeglądarce (`reviewState` w `App.vue`) na danych, które front i tak ma — ta sama reguła w dwóch językach, z odsyłaczem po obu stronach; endpoint tylko po to, żeby front zapytał o coś, co już wie, nie powstał.

Trzecia ścieżka to **pytanie o otwarty plik**: `task: "ask"` w tym samym adapterze, ten sam zawężony kontekst, walidacja na 1–6 zdań. `POST .../summary/ask` przyjmuje w ciele ścieżkę, pytanie i opcjonalny zaznaczony fragment; ścieżka przechodzi tę samą allowlistę co wyjaśnienie, a pytanie i fragment mają twarde limity (1000 i 4000 znaków) sprawdzane **przed** jakimkolwiek I/O — puste albo za długie pytanie nie kosztuje ani zapytania do Azure DevOps, ani uruchomienia modelu. Odrzucenie leci jako `ChecklistException` 400, bo `Execute` ma już dla niego gałąź.

Historię składa backend, nigdy klient: `FileQuestionService` czyta zapisane tury, przepuszcza je przez `ContentFreshness` względem bieżącego blobu pliku i bierze ostatnie trzy. Dzięki temu (a) nie da się podsunąć modelowi zmyślonej „poprzedniej odpowiedzi”, i (b) tura dotycząca wersji pliku, której już nie ma, zostaje w wątku do przeczytania, ale nie wraca do promptu — odpowiedź oparta na niej opisywałaby linie, których nie ma. Pytanie, zaznaczenie i wcześniejsze tury jadą w `context`, nigdy w `instruction`; to ta sama granica co przy Summary, tylko pierwszy raz po jej niezaufanej stronie stoi tekst napisany przez użytkownika, a nie przez repozytorium. Zaznaczenie jest brane na słowo — cały plik i tak jest w kontekście, więc fragment jest wskaźnikiem, nie nową informacją (`ponytail:` w `FileQuestionService`, sufit: da się „zaznaczyć” tekst spoza pliku).

W przeglądarce rozmowa siedzi w **szufladzie po prawej** (`position: fixed`), a nie w bloku nad diffem: blok spychał kod z ekranu dokładnie wtedy, gdy się go czytało, a szuflada nakłada się i niczego nie przesuwa. Otwiera ją przycisk „Zapytaj o plik” z licznikiem tur, klawisz `a` (ten sam zamyka) albo prawy przycisk na zaznaczeniu w Monaco (akcja `prcockpit.ask`, obie strony diffu) — ten ostatni dołącza fragment i zawsze otwiera, bo właśnie o to poprosiłeś. `Esc` zamyka szufladę przed każdą inną warstwą. Zapisany wątek **nie** otwiera jej sam: plik, o który pytałeś wczoraj, nie ma zasłaniać diffu, gdy do niego wracasz. Wysyłka i odczyt wątku jadą na liczniku `diffRequestId`, więc odpowiedź na plik, z którego już wyszedłeś, nie pokazuje się nad plikiem, do którego wszedłeś.
Debug Check to jedno stałe pytanie i pole tekstowe zapisywane w kolumnie `DebugNote` wiersza checklisty. Zapis odpowiedzi niczego nie zaznacza, a „Pokaż, gdzie patrzeć” odsłania ranking z Summary, więc ta funkcja nie uruchamia modelu ani razu. `// ponytail:` — PRODUCT.md §9 przewiduje generowane scenariusze awarii; sufitem jest dołożenie ich do schematu Summary, jeśli stałe pytanie okaże się za słabe.

Summary ma kontrakt w wersji **2**: obok 2–5 zdań zwraca `criticalFiles` — skrót z rolą i uzasadnieniem — oraz `readingOrder`, czyli **cały** PR ułożony w kolejności czytania, same ścieżki. `SummaryRunner` sprawdza każdą pozycję względem kontekstu, który sam zbudował: ścieżka spoza listy zmienionych plików, duplikat, pusty albo dłuższy niż 200 znaków opis kończą się `502`. Limity siedzą w `SummaryContract`. Wersja 1 nie jest już przyjmowana; `SummaryStore.GetAsync` zwraca dla niej `null` zamiast błędu, więc stary zapis znaczy „wygeneruj ponownie”, a nie „PR nie działa”. We frontendzie ranking jest **propozycją**: nie dotyka `readingPath`, dopóki użytkownik jej nie przyjmie, a etykiety ról w drzewie tylko opisują wiersze.

`readingOrder` jest polem **dodanym do wersji 2**, a nie wersją 3, i to jest decyzja o pieniądzach, nie o estetyce kontraktu: oba magazyny odrzucają zapis o innej wersji schematu, więc bump unieważniłby każde zapisane wyjaśnienie pliku w każdym PR, a każde z nich to opłacone wywołanie modelu. Konsekwencję widać w UI: Summary zapisane przed tą zmianą nie ma `readingOrder`, więc tryb „wszystkie pliki” mówi to wprost i proponuje przeliczenie, zamiast pokazać kolejność, której nie dostał. `readingOrder` jest traktowane jako **podpowiedź, nie kontrakt**, i to jest różnica względem `criticalFiles`. Skrót jest krótki, a zła ścieżka w nim wysyła recenzenta do nieistniejącego pliku, więc tam obowiązuje odrzucenie. `readingOrder` ma jedną linię na zmieniony plik: przy PR o dziewięćdziesięciu plikach jedna literówka albo jedno powtórzenie wywracałoby zdania, skrót i kolejność naraz — i kazało zapłacić za przebieg drugi raz. Dlatego zła pozycja jest **pomijana**, a nie odrzucana, i nic przez to nie ginie: ścieżka spoza PR nie ma czego szukać w przejściu przez ten PR, a powtórzenie jest już ustawione. Gwarancję, której potrzebuje przejście (każda ścieżka prawdziwa, każda raz, żadnej nie brakuje), **produkujemy**, a nie przyjmujemy na wiarę: czego model nie wymienił, dopisujemy na końcu w kolejności listy zmian. Szum ląduje na końcu stabilną partycją, niezależnie od tego, co zwrócił model.

Każde odrzucenie Summary mówi, **która** reguła pękła — wersja schematu, liczba zdań, puste zdanie, za długie zdanie, za długi skrót, ścieżka spoza listy zmian, ten sam plik dwa razy, za długie `role`/`why`. Powód jest pisany u nas, a nie cytowany z modelu, więc do klienta nie wycieka nic z jego odpowiedzi; liczby w komunikacie są nasze. Jeden komunikat na dziewięć różnych usterek był `502`, z którym nie dało się nic zrobić — ta sama lekcja, którą wcześniej dał błąd „AI CLI returned invalid JSON".

Drzewo jest rozdzielone na kod i **szum**. Klasyfikacja mieszka w `FileCategory.Of` w domenie i zwraca `lockFile`, `snapshot`, `generated`, `minified`, `buildOutput` albo `null` dla zwykłego kodu. Ma **jedną** implementację i dwóch odbiorców: `PrContextBuilder` pomija te pliki w pakiecie dla AI, a `ChangedFile` wystawia tę samą wartość jako właściwość wyliczaną `Category`, więc idzie w JSON-ie bez zmiany miejsc konstrukcji, bez DTO i bez migracji. Frontend buduje z tego dwa drzewa: właściwe (`.changed-files`) i zwinięty blok „Szum (N)” (`.noise-section`). Pliki szumu nie znikają — nadal da się je otworzyć i oznaczyć — ale w `orderedPaths` idą **na końcu**, więc „następny nieobejrzany” przerabia najpierw kod.

Panel diffu pokazuje ekran startowy z opisem PR, dopóki nie wybrano pliku. Przejście do opisu (`o` albo przycisk w pasku) zapamiętuje otwarty plik, a ekran startowy pokazuje widoczny przycisk powrotu; `o` działa w obie strony. Ścieżka powrotu jest czyszczona razem z resztą stanu diffu przy zmianie PR, repozytorium lub projektu.

Skróty klawiszowe obsługuje jeden nasłuch `keydown` na `window` w fazie przechwytywania, rejestrowany w `onMounted` i usuwany w `onBeforeUnmount`. Faza przechwytywania jest konieczna, bo Monaco zatrzymuje propagację klawiszy, które obsługuje. Nasłuch oddaje zdarzenie, gdy wciśnięty jest Ctrl, Meta lub Alt, oraz gdy cel zdarzenia leży w polu tekstowym — to jedno sprawdzenie obsługuje zarówno wyszukiwarkę plików, jak i własne pole „znajdź” Monaka. Keymapa celowo nie zawiera strzałek, PageUp/Down, Home/End ani klawiszy funkcyjnych, żeby przewijanie i wyszukiwanie w edytorze zostały nietknięte. Ponieważ `j`, `k` i `m` nie przenoszą fokusu, pozycja pliku jest ogłaszana przez ukryty obszar `aria-live`.

Opis PR jest Markdownem i jest renderowany w `src/description.ts`. Tekst przechodzi przez `markdown-it` z wyłączonym surowym HTML-em (`html: false`), a wynik przez DOMPurify — dwie niezależne warstwy, bo opis pisze ktoś inny. Linki dostają `target="_blank"` i `rel="noopener noreferrer"`, obrazki-załączniki Azure DevOps są zamieniane na linki (w aplikacji i tak wyrenderowałyby się jako zepsute, bo wymagają uwierzytelnienia), a wzmianki `#1234` stają się linkami tylko wtedy, gdy PR faktycznie ma taki Work Item; wzmianki w kodzie i w istniejących linkach są pomijane. Opis pokazujemy na ekranie startowym panelu diffu, zanim wybierzesz plik.

Kolory są zdefiniowane jako zmienne CSS na `:root` i nadpisywane w bloku `prefers-color-scheme: dark`. `color-scheme: light dark` sprawia, że natywne kontrolki idą za motywem systemu bez własnego CSS. Blok `prefers-reduced-motion` wyłącza animacje i płynne przewijanie.

## Przejście prowadzone przez PR

Drugi, **dodatkowy** sposób czytania PR obok drzewa plików: PR powyżej pięciu plików kodu otwiera się na ekranie wejścia z propozycją ośmiu plików z rankingu, a nie na liście osiemdziesięciu trzech. Ranking bierze się z Summary, które **nigdy nie uruchamia się samo** — to świadoma decyzja właściciela narzędzia: każde wywołanie modelu kosztuje i ma zapadać na kliknięcie, nie przy otwarciu ekranu. Zapisane Summary wczytuje się za darmo, więc drugie wejście w PR ma propozycję od razu; brak zapisanego daje na ekranie wejścia jeden przycisk uruchamiający AI, a Summary z wcześniejszego commita jest pokazywane z ofertą przeliczenia, nie przeliczane. Propozycja nie jest decyzją — dopiero „Rozpocznij przejście” zapisuje ścieżkę czytania, zgodnie z rozróżnieniem *plik krytyczny* (propozycja AI) / *plik kluczowy* (decyzja użytkownika). Szum nigdy nie wchodzi do propozycji, choćby model go wskazał; dołożyć go można ręcznie.

**Przejście ma dwa zakresy, jedną kolejność.** „Kluczowe pliki” to skrót — ranking skalowany rozmiarem PR, bez szumu, domyślnie przycięty do długości ścieżki. „Wszystkie pliki” bierze `readingOrder` w całości: każdy zmieniony plik dokładnie raz, szum na końcu do przeklikania, bo „wszystkie” znaczy wszystkie, a lockfile na końcu to jedno kliknięcie, nie objazd. Oba zakresy czytają tę samą odpowiedź modelu i **nie uruchamiają go po raz drugi** — przełącznik nie kosztuje nic. Instrukcja prosi model o kolejność, która idzie za samą zmianą: od miejsca, gdzie się zaczyna, przez to, czego dotyka, do skutków — zmiana backendowa zwykle domena → dostęp do danych → endpoint → UI, zmiana zaczynająca się od guzika odwrotnie. Kierunek wybiera model z tego PR, bo układ katalogów jest inny w każdym recenzowanym repozytorium i heurystyka po ścieżkach zgadywałaby tam, gdzie kontekst wie. Przełączenie zakresu kasuje ręcznie odznaczone pliki, bo były zaznaczeniem na innej liście.

Tryb przejścia to ten sam panel diffu na pełnej szerokości, z ukrytym drzewem i szyną (`.pr-workspace--walk`) — czyli ta sama maszyneria Monaco, komentarzy i stref, nie druga jej kopia. Nad diffem stoi pasek z pozycją **w ścieżce**: liczy to, co przejście faktycznie przechodzi, więc mówi `Krok X z N`, nie `Plik X z N`. Pozycja w liście Azure DevOps i nazwa pliku z paska narzędzi są w tym trybie ukryte (`.pr-workspace--walk`): były drugim licznikiem o tym samym mianowniku i tą samą ścieżką dwa razy na jednym ekranie. Wyjście z przejścia jest jedno, w stopce. Akcje (przeczytane/dalej, pomiń, wstecz, wyjście) są przyklejone na dole panelu, żeby koniec pliku nie wymagał przewinięcia diffu. Skróty się nie zmieniają: `m`, `j` i `k` robią w przejściu to samo, tylko po ścieżce.

Wyjaśnienie pliku powstaje **wyłącznie na kliknięcie** — przycisk „Wyjaśnij ten plik" albo klawisz `e` — i nigdy przez samo wejście w plik. Pierwotnie przejście kupowało je z góry dla całej ścieżki, żeby wejście w plik nie miało stanu oczekiwania; przy ścieżce ośmiu plików to było tanie. Tryb całego PR zmienił rachunek: przejście dziewięćdziesięciu plików znaczyło dziewięćdziesiąt opłaconych wywołań modelu, z których większość dotyczyła plików obejrzanych przelotem albo wcale. Okno przed kursorem tylko rozkładało ten koszt w czasie, zamiast go usunąć, więc prefetch został **usunięty w całości** razem z `AbortController`, licznikiem pokoleń i mapą błędów prefetchu. Co zostało: `explanationCache` w przeglądarce, żeby powrót do pliku nie kosztował drugi raz, oraz zapis w `pr_file_explanations` po stronie backendu, dzięki któremu to samo pytanie o tę samą wersję pliku jest darmowe także po odświeżeniu. Wyjaśnienie nigdy nie wstrzymuje diffu: kod renderuje się niezależnie. O wyjaśnienie prosi się z paska nad diffem albo klawiszem `e`, a panel pod paskiem przejścia istnieje **tylko wtedy, gdy jest co w nim pokazać** — pusty, z jednym przyciskiem w środku, dublował akcję stojącą linijkę niżej. Błąd modelu zostaje przy swoim pliku i ma ponowienie.

**Trzeci zakres: runda po poprawkach.** Cykl życia PR-a to pierwsze czytanie, a potem czytanie po poprawkach, i to drugie ma własny zakres przejścia — „Od mojego przejścia". Runda liczy się **per plik, nie per PR**: należy do niej plik, którego marker zwietrzał (blob ID się nie zgadza), oraz plik bez markera, bo nieprzeczytany jest nieprzeczytany niezależnie od tego, który push go przyniósł. To ta sama reguła `reviewState`, której używa odznaka „zmienione", więc nie doszła żadna druga definicja świeżości. Zakres jest proponowany dopiero wtedy, gdy **cokolwiek zostało przeczytane na starszej głowie** — pierwsze przejście porzucone w połowie ma wszystkie markery na bieżącej głowie i rundą nie jest. Decyzja zapada w `loadFileReviews`, a nie przy pobraniu szczegółów PR, bo markery przyjeżdżają osobnym żądaniem, już po wyborze ekranu.

Runda **nie uruchamia modelu i nie pyta Azure DevOps o nic więcej**: kolejność bierze z drzewa, nie z `readingOrder`, więc działa też dla PR bez zapisanego Summary, a listę zmienionych plików ma w `details`. Każdy plik otwiera się na zmianach **od iteracji, na której był ostatnio oglądany** — `headSha` z markera mapowany na iterację po `sourceCommitSha` i podawany jako `sinceIteration` do istniejącego `/diff`. Plik bez markera nie ma od czego liczyć i dostaje pełny diff; ten sam pasek nad diffem co przy filtrze iteracji mówi, co widać, i oddaje całość jednym kliknięciem. Świadomy sufit (`ponytail`): bazą jest marker, więc dokładność rundy kończy się tam, gdzie kończy się ręczne oznaczanie — stempel rundy w bazie byłby dokładniejszy, ale to migracja i nowa trasa dla czegoś, co markery już niosą.

Domknięcie rundy po stronie komentarzy to trzeci filtr w widoku wątków — „Moje nierozwiązane". Mój jest wątek, który **założyłem**, czyli ten, którego pierwszy komentarz ma `isMine`; odpowiedź w cudzym wątku nie czyni jego zamknięcia moją sprawą. Pliki, w których autor zdążył już odpowiedzieć kodem (`movedSinceComment`), idą w tym trybie na górę. Gdy sonda tożsamości padła, każdy komentarz przychodzi jako cudzy, więc filtr **nie jest pokazywany** zamiast świecić pustą listą.

Przerwane przejście czeka: `pr_reading_paths` trzyma `Position` i `HeadCommitSha` z chwili wyboru ścieżki. Ścieżka bez `HeadCommitSha` pochodzi z szyny, nie z przejścia, i nie jest proponowana do wznowienia. Inna głowa PR niż zapisana daje wybór — wznów dotychczasową albo przelicz propozycję; ścieżka nie jest kasowana bez decyzji użytkownika. Pozycja jest przycinana do długości ścieżki przy odczycie, a plik, który wypadł z PR, wypada też ze ścieżki. Przejście domknięte (pozycja równa długości) nie proponuje już niczego i PR otwiera się normalnie.

**Ranking skaluje się z rozmiarem PR.** Dziesięć plików otwiera PR o dwudziestu plikach, ale PR o osiemdziesięciu tylko próbkuje — dziesiątka przestaje być punktem startu, a staje się losowym wycinkiem. `SummaryContract.CriticalFileLimit` daje więc mniej więcej jeden wskazany plik na cztery zmienione, z podłogą 10 i sufitem 25; powyżej sufitu lista przestaje być krótką listą. Ta sama liczba trafia do instrukcji dla modelu i do walidacji odpowiedzi, więc model nie jest proszony o więcej, niż wolno mu zwrócić. `MaxReadingPath` w magazynie to już tylko sanity bound, a nie reguła produktowa — i od trybu całego PR równy 2000, czyli tej samej stronie listy zmian, której używa klient Azure DevOps: ścieżka przez cały PR jest tak długa jak PR. Domyślna długość ścieżki przejścia rośnie wolniej — jeden plik na osiem zmienionych, między 8 a 12 — bo przejście bez widocznego końca jest tym, co miało zastąpić. Reguła rankingu żyje w dwóch językach (`criticalFileLimit` w `App.vue`), tak jak reguła nieaktualności.

Długości ścieżki i rankingu są nazwanymi stałymi w `App.vue` z komentarzem `// ponytail:`, nie pozycjami w konfiguracji: jednoosobowe narzędzie lokalne nie ma pliku ustawień, a zakładanie go dla dwóch liczb kosztowałoby więcej, niż daje.

## Trwałość

`ChecklistStore` zapisuje sześć ręcznych pól w lokalnej bazie SQLite. Wiersz identyfikują organizacja Azure DevOps, projekt, ID repozytorium i ID PR. `GET .../checklist` zwraca stan, a `PUT .../checklist/{item}` zapisuje jedno pole i zwraca cały stan; `Ready` jest wyłącznie ręczną decyzją użytkownika. Dane leżą w lokalnej bazie SQL Server, obsługiwanej przez Entity Framework Core. Połączenie wskazuje `ConnectionStrings:PrCockpit`; musi zawierać jawny `Initial Catalog`, bo bez niego EF sięga do domyślnej bazy loginu i zakłada tabele tam. Migracje są stosowane przy starcie aplikacji, więc pierwsze uruchomienie tworzy bazę i utrzymuje ją w zgodzie z modelem. To zastąpiło ręczne `CREATE TABLE IF NOT EXISTS` wykonywane przy każdej operacji, które nie potrafiło rozwinąć schematu: dołożenie kolumny do istniejącej bazy po cichu nic by nie zrobiło. Frontend odrzuca spóźnione odpowiedzi checklisty po przejściu do innego PR. Znaczniki „Obejrzałem” i ścieżka czytania są zapisywane przez `ReviewProgressStore` w tej samej bazie, w dwóch tabelach: `pr_file_reviews` (wiersz na przeczytany plik) i `pr_reading_paths` (cała ścieżka jako JSON). Obecność wiersza oznacza „przeczytane”, więc odznaczenie to `DELETE`, a liczenie to `COUNT(*)`. Ścieżka czytania leży jako JSON, bo przestawianie kolejności wierszy wymagałoby transakcji, a repozytorium nie używa żadnej; jest re-walidowana przy odczycie tak samo jak zapisane Summary. `ProjectKnowledge` nie istnieje jeszcze w kodzie.

Przy oznaczaniu pliku zapisujemy `reviewed_blob_id` — identyfikator blobu z `changeEntries[].item.objectId`, który Azure DevOps i tak zwraca przy liście zmian — oraz `reviewed_head_sha` jako wariant zapasowy. Znacznik staje się nieaktualny **wyłącznie przy pozytywnym dowodzie zmiany**: blob się nie zgadza albo, gdy blobu brak po którejś stronie, nie zgadza się SHA głowy. Gdy nie ma czego porównać, znacznik zostaje — nagabywanie bez powodu jest gorsze niż lekko optymistyczny ptaszek. Blob ID zmienia się wtedy i tylko wtedy, gdy zmieniła się treść tego pliku; porównanie po samym SHA głowy, jak robi Summary, jest poprawne dla całego PR, ale dla pojedynczych plików unieważniałoby wszystkie znaczniki po jednym commicie. Plik nieaktualny liczy się jako nieprzeczytany dla licznika, filtra i „następnego nieobejrzanego”, ale renderuje własną odznakę zamiast wracać do pustki. Liczba wierszy na PR jest ograniczona do 2000 wewnątrz samego `INSERT`, więc limit nie kosztuje dodatkowego zapytania; istniejący wiersz zawsze przechodzi, żeby ponowne oznaczenie nigdy nie zostało zablokowane. Mianownik `x/y plików` na liście PR pochodzi z `changed_files_count` dosyłanego przez frontend przy każdym oznaczeniu, bo lista PR z Azure DevOps nie zawiera liczby zmienionych plików, a dociąganie jej per wiersz łamałoby zasadę pobierania na żądanie.

Lista aktywnych PR pobiera postęp z `GET /api/projects/{project}/repositories/{repositoryId}/pull-requests/checklist-progress`. `ChecklistStore` wykonuje jedno zapytanie SQLite ograniczone do organizacji, projektu i repozytorium; odpowiedź zawiera tylko ID PR z zapisanym wierszem oraz sumę sześciu pól (`completedCount`). Frontend łączy wynik z listą Azure DevOps i pokazuje `0/6`, gdy PR nie ma zapisu. Stan ładowania i błędu jest widoczny osobno od listy PR; błędny odczyt nie jest przedstawiany jako zerowy postęp. Identyfikator żądania chroni listę przed spóźnioną odpowiedzią po zmianie projektu lub repozytorium. Po powrocie ze szczegółów frontend ponownie pobiera postęp, aby uwzględnić ręcznie zapisane kroki.

`PrCockpitContext` mapuje sześć tabel (`pr_checklists`, `pr_summaries`, `pr_file_reviews`, `pr_reading_paths`, `pr_file_explanations`, `pr_file_questions`), a encje leżą w `Persistence/Entities`. Każdy wiersz jest kluczowany organizacją, projektem, repozytorium i PR — wspólna klasa bazowa `PullRequestScopedRow` wymusza ten kształt. Wyjątkiem jest `pr_file_questions`: to jedyna tabela, która **dopisuje**, a nie nadpisuje, więc klucz jest surogatowy (`Id` identity), a zakres plus ścieżka są indeksem. Klucz naturalny musiałby zawierać zegar, a dwa wiersze w tym samym tyknięciu byłyby naruszeniem klucza zamiast drugiego pytania. Wątek czyta się po `Id`, nie po `AskedAt` — tabela tylko dopisuje, więc kolejność wstawienia jest kolejnością chronologiczną, a `DateTimeOffset` i tak nie sortuje się na SQLite, na którym stoją testy. Magazyny są rejestrowane jako scoped, bo zależą od scoped kontekstu. W `Execute` doszły `SqlException` i `DbUpdateException` mapowane na 503.

Testy magazynu działają na SQLite w pamięci, żeby `dotnet test` nie wymagał serwera bazy na maszynie. To świadoma różnica względem produkcji: testy pinują zachowanie magazynu, a poprawność samego schematu potwierdza zastosowanie migracji na rzeczywistym SQL Server.

PAT jest rozwiązaniem lokalnym, krótkoterminowym. Przed udostępnieniem aplikacji poza własną maszynę trzeba dodać Microsoft Entra i autoryzację API. Obecny profil uruchomieniowy nasłuchuje na localhost. Testy klienta używają atrapy `HttpMessageHandler`.
